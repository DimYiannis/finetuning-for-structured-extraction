## Open decisions

Must be settled before the eval split is frozen, since they change what every row measures:

- **Chat template.** Upstream feeds the prompt as a raw string. SFT on chat-formatted data applies Qwen3's chat template, so inference must too, or train and serve diverge. Applying it makes the "base + constrained" row differ slightly from upstream.
- **Thinking mode.** With the chat template, Qwen3 thinks by default; `enable_thinking=False` keeps `<think>` blocks out of the output budget.
- **Deterministic decoding.** Qwen3's shipped `generation_config` samples; eval should run greedy so numbers are reproducible.

## Known limitations

- The identifier regex cannot represent multi-word concepts from prose (e.g. "LoRA adapters"); text chunks are forced into single-token names.
- Models load on CPU in fp32 by default; no device placement or adapter loading yet.


# qwen3-triple-extraction — Build Order

Companion to `qwen-finetune-spec.md`. That file says *what* to build; this says *in what order*, and why the order matters.

**Ordering principle:** metrics before data, eval set before training set, baselines before training. At every point you should have something defensible even if the next step breaks.

---

## 1. Lift the pieces out of constrained-graphrag

Copy across — don't import. This is a standalone repo and a cross-repo dependency will bite you later.

- [ ] Relation schema (node labels + relation types) → `data/schema.py`
- [ ] The extraction prompt used at inference time
- [ ] The constrained generation function (the decoding path only, not the graph pipeline)
- [ ] A batch of source chunks

~30 minutes. If the constrained generation is tangled into the pipeline and hard to separate, see the fallback in step 4.

---

## 2. Write `schema.py` and the eval metrics FIRST

Before any data. Before any training.

- [ ] `schema.py` — node labels and relation types, single source of truth, imported everywhere
- [ ] `evaluate.py` — parse JSON, validate against schema, compare triple sets, return validity rate + precision/recall

Test it on hand-written examples. Writing the evaluator first means your dataset format and your metrics agree by construction rather than by luck.

---

## 3. Build the eval split before the training split

- [ ] Take 50–100 chunks
- [ ] Generate candidate triples with a larger model
- [ ] **Hand-correct all of them.** This is ground truth — every number in the project is measured against it
- [ ] Freeze, commit as `data/eval.jsonl`, never regenerate

---

## 4. Run the baselines

Two rows, before any training exists:

- [ ] Base model, unconstrained
- [ ] Base model + constrained decoding (the current constrained-graphrag approach)

Save raw outputs to `results/baseline/`, not just aggregates. You now have a result even if everything after this goes wrong.

*Fallback:* if the constrained-decoding path can't be cleanly lifted, drop that row and compare base-unconstrained vs fine-tuned-unconstrained. Weaker story, still a real result, and the row can be added later.

---

## 5. Build the training split

- [ ] 300–800 chunks
- [ ] Generate candidates, **spot-check** rather than exhaustively correcting
- [ ] Save as `data/train.jsonl`

This is the bulk of the time. It's fine for it to be noisier than the eval set.

---

## 6. Train

- [ ] Unsloth Qwen3 notebook, swap in the JSONL
- [ ] Watch the loss curve, save the plot
- [ ] Record every hyperparameter (rank, alpha, target modules, LR, epochs)

Minutes, not hours, on 0.6B. If loss collapses immediately or plateaus flat, inspect the data formatting before touching hyperparameters.

### Local option: MacBook M2, 8 GB RAM

Alternative to the Colab T4. Same LoRA approach; the settings are chosen to fit in memory.

**Setup**

- Apple Silicon: CPU and GPU share one RAM pool (unified memory), so the 8 GB is split between macOS and training. Realistic training budget: ~4–5 GB.
- Device: MPS (Apple's GPU backend), fp32.
- Env var `PYTORCH_ENABLE_MPS_FALLBACK=1`: ops MPS doesn't support run on the CPU instead of crashing.
- Close Chrome/Slack/other heavy apps before training. Keep the Mac plugged in and cool; it throttles under sustained load.

**What fits on 8 GB**

| Approach | Memory | Fits? |
|---|---|---|
| Full fine-tune, fp32 | ~10 GB or more | No |
| LoRA, fp32 base | ~4–5 GB | Yes, small batches |
| LoRA, bf16 base | ~2–3 GB | Yes; check MPS bf16 support on your macOS version |

**Starting settings**

| Setting | Value |
|---|---|
| `per_device_train_batch_size` | 1 (2 at most) |
| `gradient_accumulation_steps` | 8–16 |
| `max_seq_length` | 256–512 |
| Gradient checkpointing | on |
| LoRA rank | 8–16 |
| LoRA target modules | `q_proj`, `v_proj` |

**Watch while training**

- Activity Monitor → Memory tab → **Memory Pressure**. Green = fine. Yellow/red = it is swapping to disk; reduce batch size or sequence length.
- `MPS backend out of memory` error: shrink batch size or sequence length first.
- If the Mac struggles, fall back to the Colab T4 (~15 GB VRAM), which is also faster.
